## 1. 核心约束：站点挂在哪个路径下

**这是本项目部署最容易踩的坑，先看这一节。**

`npm run build` 的产物**可以挂在任意路径**（根路径 `/` 或子路径 `/iot/`），不需要为不同路径分别构建。原因是 [webpack.config.js:38](../webpack.config.js#L38) 生产模式用的是：

```js
publicPath: isProd ? "auto" : "/"
```

webpack 5 的 `"auto"` 会在**运行时**按当前脚本自身的 URL 推导资源前缀：页面在 `/iot/` 下，chunk 就从 `/iot/js/` 取；页面在根路径，就从 `/js/` 取。

**唯一要求：`index.html` 和 `js/` `css/` `assets/` 必须保持同级的相对位置**（即整个 `dist/` 原样放到目标路径下），别把 `index.html` 单独挪走。

### 历史坑（2026-08-14 前的构建产物）

[src/main.js](../src/main.js) 曾在入口处硬编码覆盖掉上面的 `"auto"`：

```js
__webpack_public_path__ = process.env.NODE_ENV === 'production' ? '/iot/' : '/'
```

导致老产物**只能挂在 `/iot/` 下**。挂到根路径会出现一种很迷惑的故障：

1. 首屏能加载（`index.html` 里 `<script src="js/main.xxx.js">` 是**相对路径**，不走 `__webpack_public_path__`）
2. 但一进路由，懒加载 chunk 请求 `/iot/js/xxx.js` → **404**
3. 404 触发 [src/router/index.js](../src/router/index.js) 的 `ChunkLoadError` 兜底，hash 模式下跳到不带 `#` 的真实路径
4. 服务器上没有该路径 → 白屏 404

现在 `main.js` 改成**默认不覆盖**，只有显式设置 `VUE_APP_BASE_PATH` 时才覆盖（用于静态资源放 CDN / 独立域名的场景，值必须以 `/` 结尾）。`.env.production` 里该项留空即为 `"auto"`。

> 如果你手上有 2026-08-14 之前构建的 `dist/`，它仍然带着 `/iot/` 硬编码，**必须挂在 `/iot/` 下**，或者重新构建。判断方法：`grep -o '/iot/' dist/js/main.*.js | head` 有输出就是老产物。

## 2. 构建

```bash
cd iot_server_frontend
npm ci                 # 或 npm install
npm run build          # webpack --mode production，产物在 dist/
```

产物结构：

```
dist/
├── index.html          # 相对路径引用 js/ css/
├── config.json         # 运行时配置，见第 3 节
├── favicon.ico / favicon.svg
├── assets/             # 图片等
├── css/
└── js/                 # main.*.js + 按路由切分的懒加载 chunk
```

构建环境需要 Node 18+（已验证 18.19.1 与 20.17.0）。构建产生的 asset size 警告可忽略。

正式/测试站点使用 backend 制品 `dist/`。纯客户端 Demo 必须显式执行 `npm run build:demo`，输出到独立的 `dist-demo/`；两种制品不能混用。

打包上传：

```bash
tar -czf frontend-dist.tar.gz -C dist .
scp frontend-dist.tar.gz USER@HOST:/tmp/
ssh USER@HOST 'mkdir -p /var/www/iot && tar -xzf /tmp/frontend-dist.tar.gz -C /var/www/iot'
```

## 3. 运行时配置 `config.json`

前端**不需要为了换后端地址重新构建**。[src/utils/config.js](../src/utils/config.js) 在启动时 fetch `config.json`：

```json
{
  "apiBase": "auto",
  "uploadBaseUrl": "auto"
}
```

| 值 | 行为 |
|---|---|
| `"auto"`（默认） | 使用**同源** `/api/v1`，交给 nginx 反代。**部署形态 A 用这个** |
| 绝对地址 | 跨域直连后端，例 `"http://192.168.1.38:8201/api/v1"`。**部署形态 B 用这个** |

`uploadBaseUrl` 留 `"auto"` 时自动取 `apiBase` 去掉 `/api/v1` 的部分。

WebSocket 地址由 `getWebSocketApiBase()` 从 `apiBase` 推导（`http:`→`ws:`，`https:`→`wss:`），无需单独配置。

**探测路径有两条**（[config.js:8-14](../src/utils/config.js#L8-L14)）：先按 `document.baseURI` 相对解析 `config.json`，再试绝对的 `/config.json`。挂在 `/iot/` 下时建议**两个位置各放一份**，避免依赖解析顺序。

修改 `config.json` 后刷新页面即可生效，**不用重新构建、不用重启**。给它加 `Cache-Control: no-cache`，否则浏览器会拿旧的。

## 4. 部署形态 A：nginx 同源反代（推荐）

前端和 API 同源，**没有 CORS 问题**，WebSocket 也自动同源。`config.json` 保持 `"auto"`。

```nginx
server {
    listen 80;
    server_name your.host;

    # 前端挂在 /iot/ 下 —— 必须，见第 1 节
    location /iot/ {
        alias /var/www/iot/;
        # SPA fallback，见第 6 节
        try_files $uri $uri/ /iot/index.html;

        location ~* \.(css|js|jpg|jpeg|png|gif|ico|svg|woff|woff2|ttf|eot)$ {
            expires 1y;
            add_header Cache-Control "public, immutable";
        }
        location ~* /(index\.html|config\.json)$ {
            add_header Cache-Control "no-cache";
        }
    }

    location = / {
        return 302 /iot/;
    }

    # API 反代到后端
    location /api/ {
        proxy_pass http://127.0.0.1:8201;
        proxy_set_header Host              $host;
        proxy_set_header X-Real-IP         $remote_addr;
        proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;

        # WebSocket
        proxy_http_version 1.1;
        proxy_set_header Upgrade    $http_upgrade;
        proxy_set_header Connection "upgrade";

        proxy_connect_timeout 60s;
        proxy_send_timeout    60s;
        proxy_read_timeout    60s;
        client_max_body_size  50M;      # 文件上传
    }

    # 上传文件直读（后端 uploads）
    location /uploads/ {
        proxy_pass http://127.0.0.1:8201;
        client_max_body_size 50M;
    }
}
```

```bash
sudo nginx -t && sudo systemctl reload nginx
```

这种形态下后端可以只绑 `127.0.0.1`，不暴露到局域网。

## 5. 部署形态 B：独立静态服务 + 跨域

**没有 sudo、动不了 nginx 时用这个。** 前端和后端各占一个端口，浏览器跨域直连。

### 5.1 目录结构

`dist/` 原样铺在站点根目录即可（publicPath 为 `"auto"`，chunk 会自动按 `/js/` 定位）：

```
/opt/iot/frontend/          # ← dist/ 的全部内容
├── index.html
├── config.json
├── assets/ css/ js/
└── favicon.ico  favicon.svg
```

`config.json`：

```json
{
  "apiBase": "http://BACKEND_HOST:8201/api/v1",
  "uploadBaseUrl": "http://BACKEND_HOST:8201"
}
```

### 5.2 静态服务

`python3 -m http.server` **不能直接用**——它没有 SPA fallback（见第 6 节）。用下面这个：

```python
#!/usr/bin/env python3
"""前端静态服务。

webpack output.publicPath 为 "auto"，产物挂根路径即可，chunk 会按脚本 URL 自动定位。
保留 SPA fallback：无扩展名且找不到的路径回 index.html，兜住深链和刷新。
"""
import os
import sys
from http.server import SimpleHTTPRequestHandler, ThreadingHTTPServer

ROOT = "/opt/iot/frontend"
PORT = int(sys.argv[1]) if len(sys.argv) > 1 else 8200


class Handler(SimpleHTTPRequestHandler):
    def __init__(self, *a, **kw):
        super().__init__(*a, directory=ROOT, **kw)

    def send_head(self):
        path = self.path.split("?", 1)[0].split("#", 1)[0]
        local = os.path.join(ROOT, path.lstrip("/"))
        if not os.path.exists(local) and "." not in os.path.basename(path):
            self.path = "/index.html"
        return super().send_head()

    def end_headers(self):
        if self.path.endswith((".html", "/")) or self.path.endswith("config.json"):
            self.send_header("Cache-Control", "no-cache")
        super().end_headers()


if __name__ == "__main__":
    ThreadingHTTPServer(("0.0.0.0", PORT), Handler).serve_forever()
```

> 挂子路径（如 `/iot/`）时，把 `dist/` 放进 `ROOT/iot/`，并在 `send_head` 里加一条 `/` → `/iot/` 的 302、fallback 目标改成 `/iot/index.html` 即可，其余不变。

```bash
setsid nohup python3 /opt/iot/serve.py 8200 >> /opt/iot/logs/frontend.log 2>&1 < /dev/null &
```

访问日志会写进 `frontend.log`，排查资源 404 时非常有用。

### 5.3 后端必须放行来源

后端 `.env` 里 `ALLOWED_ORIGINS` 要填**前端的源**（含端口），并且后端要绑 `0.0.0.0`：

```
ALLOWED_ORIGINS=http://192.168.1.38:8200
```

验证预检返回了正确的 `Access-Control-Allow-Origin`，见第 7 节。

## 6. SPA fallback 为什么仍然要配

路由是 **hash 模式**（[src/router/index.js:203](../src/router/index.js#L203) `mode: 'hash'`），正常 URL 形如 `/#/dashboard`，`#` 后面的部分服务器看不到，**单看路由是不需要 fallback 的**。

但仍建议配上，兜两种情况：

1. 用户手动输入或从别处复制了 `/dashboard`、`/login` 这类不带 `#` 的路径
2. 历史上 [src/router/index.js](../src/router/index.js) 的 `ChunkLoadError` 兜底会执行 `window.location.href = targetPath`，而 hash 模式下 `fullPath` 不带 `#`（形如 `/login?redirect=%2Fdashboard`），直接跳就是 404 白屏

第 2 点已在 2026-08-14 修复（hash 模式下改为写 `location.hash` 再 `reload()`），但**老构建产物仍带着这个缺陷**，且第 1 点永远存在。fallback 的成本只有一行，配上更稳。

## 7. 验证清单

```bash
F=http://FRONTEND_HOST:8200

# 站点挂子路径时，把下面的 $F/ 换成 $F/iot/

# 1) 首页
curl -s -o /dev/null -w '%{http_code}\n' $F/

# 2) index.html 引用的静态资源全部 200
curl -s $F/ | grep -oE '(src|href)="((js|css|assets)/[^"]+)"' | grep -oE '(js|css|assets)/[^"]+' | \
while read a; do echo "$(curl -s -o /dev/null -w '%{http_code}' $F/$a) /$a"; done

# 3) 懒加载 chunk：直接遍历部署目录下的全部产物，一个都不能漏
#    （在服务器上执行；这是最可靠的校验，能发现旧产物残留和上传不全）
cd /opt/iot/frontend
for f in js/* css/* assets/*; do
  code=$(curl -s -o /dev/null -w '%{http_code}' "http://127.0.0.1:8200/$f")
  [ "$code" != "200" ] && echo "!! $code /$f"
done; echo "遍历完成"

# 4) SPA fallback：这几个都必须 200 且返回 index.html
for p in /login '/login?redirect=%2Fdashboard' /dashboard; do
  echo "$(curl -s -o /dev/null -w '%{http_code}' "$F$p") $p"
done

# 5) config.json
curl -s $F/config.json; echo

# 7) 跨域部署时，后端预检必须回显前端源
curl -s -i -X OPTIONS http://BACKEND_HOST:8201/api/v1/auth/login \
  -H "Origin: $F" -H 'Access-Control-Request-Method: POST' | grep -i access-control-allow-origin
```

**浏览器侧还要看一眼 F12**：Network 面板不能有 404 的 `js/*.js`，Console 不能有 `Loading chunk ... failed`。

功能上至少走一遍：登录 → 仪表盘出图 → 切换语言 → 深浅主题 → 刷新页面不掉登录。

## 8. 常见问题

| 现象 | 原因 | 处理 |
|---|---|---|
| 首屏能开，一点菜单就白屏跳 `/login` 404 | 用的是 2026-08-14 之前的老产物（带 `/iot/` 硬编码）却挂在根路径 | 重新构建，或把站点挂到 `/iot/`。见[第 1 节](#1-核心约束站点挂在哪个路径下) |
| Console 报 `Loading chunk N failed` | 同上；或发版后浏览器拿了旧 index.html 引用已删除的 chunk | 给 `index.html` 加 `no-cache` |
| 发版后个别 chunk 404 | 上传时没清干净旧产物，或只传了部分文件 | 目标目录先清空再整包上传；用[第 7 节](#7-验证清单)第 3 步遍历校验 |
| 刷新页面 404 | 缺 SPA fallback | 见[第 6 节](#6-spa-fallback-为什么仍然要配) |
| 登录报 CORS / Network Error | 后端 `ALLOWED_ORIGINS` 没填前端源（含端口） | 改后端 `.env` 重启 |
| 页面能开但所有接口 404 | `config.json` 的 `apiBase` 不对，或用了 `"auto"` 但没配 nginx 反代 | 按部署形态选对 `apiBase` |
| 改了 `config.json` 不生效 | 被浏览器缓存 | 加 `Cache-Control: no-cache`，强刷 |
| 字体加载慢 / 样式轻微不同 | `index.html` 引用了 Google Fonts 外链，内网不通外网时回退系统字体 | 不影响功能；要彻底离线可把字体本地化 |
| 上传/下载文件 404 | `uploadBaseUrl` 没配，或 nginx 没反代 `/uploads/` | 见第 3、4 节 |

## 9. 纯客户端 Demo 部署

Demo 是零后端静态站点，不适用第 4、5 节的 API 反代或跨域配置。它必须部署在独立 HTTPS 域名的根路径，`config.json` 保持 `appMode: "demo"`、`apiBase: "auto"` 和 `uploadBaseUrl: "auto"`，所有 `/api`、`/uploads`、`/emqx` 请求由服务器直接返回 404。

仓库提供以下发布入口：

```bash
cp .deploy.example .deploy.local
# 只在 .deploy.local 中填写 IOT_DEPLOY_DEMO_*，不要提交该文件
bash scripts/deploy-demo.sh

# 可单独检查已有制品或线上站点
npm run verify:demo-artifact
npm run smoke:demo -- https://demo.example.com
```

`scripts/deploy-demo.sh` 要求干净的 Git checkout，构建并离线校验 `dist-demo/` 后上传到 `releases/<release-id>/`，再原子切换 `current`；线上 smoke 失败会切回发布前记录的精确版本。Nginx 基线见 [`nginx.demo.example.conf`](../nginx.demo.example.conf)，完整安全边界和浏览器验收见 [Demo 模式开发与部署方案](Demo模式-开发与部署方案.md)。首次上线前仍须补齐真实域名、TLS 证书、独立 SSH 凭据，并在目标服务器执行 Nginx 配置检查。
