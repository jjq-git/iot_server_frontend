## 1. 测试目标

本测试用于确认以下完整通信闭环可用：

```text
前端操作
  → 后端 REST API
  → MQTT 下行
  → 主机/网关
  → CAN 总线
  → CANopen 节点
  → CAN 响应或状态上报
  → 主机/网关
  → MQTT 上行
  → 后端/WebSocket
  → 前端状态、ACK、日志或快照
```

需要覆盖的 CANopen 能力包括：

- 心跳、Boot-up 和节点在线状态；
- NMT Start、Stop、Reset 状态控制；
- SDO 读取、写入、回读与异常响应；
- PDO 或等效实时状态上报；
- EMCY 紧急报文；
- 多节点隔离；
- 断线、超时与恢复；
- 平台命令 ACK、日志、审计和前端展示一致性。

`npm run test:canopen` 只验证前端 CANopen 工具函数，不代表整体通信已经通过。整体通信必须在真实设备或协议仿真环境中执行端到端测试。

## 2. 测试边界与通信链路

测试至少需要观察以下四个位置：

| 观察点 | 推荐工具 | 用途 |
|---|---|---|
| 前端/API | 浏览器开发者工具 Network、页面命令状态 | 确认请求参数、HTTP 结果和 `command_id` |
| MQTT/WebSocket | 前端“MQTT 消息流”、MQTT 客户端 | 确认上下行消息、状态、心跳和 ACK |
| 主机/网关 | 前端“串口日志”、主机本地日志 | 确认 MQTT 命令已转换为 CANopen 操作 |
| CAN 总线 | CAN 分析仪、USB-CAN | 确认 COB-ID、Node ID、数据和时序正确 |

如果没有 CAN 分析仪，可以完成平台功能验收，但不能完全证明总线报文和时序符合 CANopen 规范。

## 3. 前端测试页面

项目使用 Hash 路由。独立部署在 `/iot/` 时，完整地址示例为：

```text
https://<前端域名>/iot/#/debug/device-control
```

开发环境通常使用：

```text
http://<开发地址>/#/debug/device-control
```

### 3.1 核心页面

| 测试内容 | 菜单/页面 | 路由 | 主要操作 |
|---|---|---|---|
| 节点控制、SDO 写入、NMT、ACK | 系统调试 → 设备控制台 | `/debug/device-control` | 选择主机、节点、OD 规范；刷新状态；下发安全属性；执行 NMT |
| 心跳、PDO/状态、MQTT 上下行 | 系统调试 → MQTT 消息流 | `/debug/mqtt-stream` | 选择主机；查看 `status`、`heartbeat`、`command_ack`、`emcy` 等消息 |
| SDO 批量读取、OD 快照 | 系统调试 → OD 诊断 | `/debug/od` | 选择主机、节点、目标和规范版本；执行 OD Dump；检查新快照 |
| EMCY 验证 | 历史数据 → EMCY 日志 | `/history/emcy` | 选择主机；刷新；核对节点、错误码、寄存器和 5 字节数据 |

### 3.2 辅助页面

| 测试内容 | 菜单/页面 | 路由 | 用途 |
|---|---|---|---|
| 主机和实时节点发现 | 系统调试 → 设备 | `/debug/devices` | 确认主机在线及最近 120 秒实际发过消息的节点 |
| 主机日志 | 历史数据 → 串口日志 | `/history/serial` | 定位主机收发、解析、超时和 CAN 错误 |
| 传感器历史 | 历史数据 → 传感器数据 | `/history/sensors` | 验证状态数据持续入库和趋势连续性 |
| 节点基础信息 | 设备管理 → 节点设备 | `/devices/nodes` | 核对节点绑定、型号、Node ID 和在线状态 |
| 节点详情 | 设备管理 → 节点详情 | `/devices/nodes/<nodeId>` | 核对心跳间隔、型号、绑定关系和最新状态 |

scope 内设备运维页面对 `platform_admin`、`admin`、`maintainer` 开放；全局 MQTT 消息流、控制器原始控制以及型号/主机/节点平台台账仅对 `platform_admin` 开放。执行包含这些平台页面的完整测试套件时必须使用 `platform_admin`，不要绕过前端权限。

## 5. 测试环境与准备条件

### 5.1 硬件条件

- 一台已注册且在线的主机/网关；
- 至少一个 CANopen 节点，建议准备两个不同 Node ID 的节点用于隔离测试；
- 稳定电源；
- CAN_H、CAN_L、GND 接线正确；
- 总线两端各有一个 120Ω 终端电阻；
- 所有设备波特率一致；
- Node ID 唯一且处于允许范围；
- 推荐准备 USB-CAN 或 CAN 分析仪；
- 有紧急停机或断电手段。

断电后测量 CAN_H 与 CAN_L 之间的等效电阻，正常双终端总线通常应接近 60Ω。实际结果受设备内部电路影响，不能只凭该数值判断全部硬件正常。

### 5.2 软件条件

- 前端、后端、MQTT 服务和数据库均已启动；
- 主机已连接 MQTT，前端能看到主机在线；
- 节点已绑定正确的 CANopen 型号编码；
- 对应 OD 规范及版本已上传；
- 测试账号角色为 `platform_admin`；若仅验证 scope 内设备运维子集，可使用 `admin` 或 `maintainer`；
- 浏览器时间、服务器时间和主机时间基本一致；
- 能查看后端日志、主机日志和 MQTT 消息；
- 测试前记录当前前端、后端、主机固件和节点固件版本。

### 5.3 安全测试属性

执行写入测试前，由节点固件人员指定至少两个属性：

| 属性 | 要求 | 示例 |
|---|---|---|
| 安全可读写属性 | 改变后不会造成人身或设备危险，支持回读和恢复 | 指示灯使能、亮度、测试模式 |
| 只读属性 | 可用于验证禁止写入 | 固件版本、硬件版本、运行时间 |

不要在无人监护时测试电机、锁控、加热、制冷、大功率负载、紧急停止解除等属性。

### 5.4 测试前检查清单

- [ ] 主机在线；
- [ ] 节点供电正常；
- [ ] Node ID 和波特率已确认；
- [ ] 型号及 OD 规范版本正确；
- [ ] MQTT 消息流能够建立 WebSocket 连接；
- [ ] CAN 分析仪已开始记录，或已确认本轮不做总线规范验收；
- [ ] 已记录所有待写属性的原值；
- [ ] 已确认恢复步骤和紧急停止方式；
- [ ] 测试环境没有连接可能被误动作影响的真实业务负载。

## 7. 测试执行顺序

必须从低风险到高风险执行：

1. 前端工具函数测试；
2. 主机、节点和规范绑定检查；
3. 心跳与在线状态；
4. NMT Start/Stop/Reset；
5. SDO 读取和 OD Dump；
6. 安全属性 SDO 写入和回读；
7. PDO/实时状态；
8. EMCY；
9. 断线和恢复；
10. 多节点隔离；
11. 稳定性和性能。

基础在线、心跳或 NMT 不通过时，不应继续执行写入、故障注入和长稳测试。

## 8. 详细测试用例

### TC-CAN-001 前端 CANopen 工具函数

**页面：** 无，命令行执行。

**步骤：**

```bash
npm run test:canopen
```

**预期结果：**

- 所有 Node.js 测试通过；
- 型号编码只接受目录中存在的型号；
- OD Dump 不会误用上一次旧快照；
- 页面能够从平铺、节点级或嵌套状态中读取属性值。

**说明：** 本用例只验证前端逻辑，不可代替 TC-CAN-002 至 TC-CAN-016。

### TC-CAN-002 主机与节点准备状态

**页面：** `/debug/devices`、`/devices/nodes`。

**步骤：**

1. 打开“系统调试 → 设备”，确认目标主机在线；
2. 检查最近 120 秒实时节点列表；
3. 打开“设备管理 → 节点设备”；
4. 核对主机绑定、Node ID、型号、心跳间隔和固件版本。

**预期结果：**

- 主机状态为在线；
- 目标 Node ID 能被实时发现；
- 节点绑定信息与实物一致；
- 不存在重复 Node ID；
- 型号编码可以匹配 OD catalog。

### TC-CAN-003 心跳与在线状态

**页面：** `/debug/mqtt-stream`，辅助使用 `/debug/device-control`。

**步骤：**

1. 打开“MQTT 消息流”并选择目标主机；
2. 关闭“隐藏心跳”或在消息类型中主动选择“心跳”；
3. 连续观察至少 5 个心跳周期；
4. 记录相邻心跳时间、Node ID、在线状态和 NMT 状态；
5. 在设备控制台刷新状态。

**预期结果：**

- 心跳周期与配置一致，允许误差由项目协议约定；
- 心跳持续来自正确主机和 Node ID；
- 前端节点状态为在线；
- 无周期性误离线、重复节点或状态串线；
- CAN 分析仪可看到对应 `0x700 + Node ID` 心跳帧时，数据字节与 NMT 状态一致。

### TC-CAN-004 NMT Start

**页面：** `/debug/device-control`、`/debug/mqtt-stream`。

**步骤：**

1. 选择目标主机、节点和 OD 规范；
2. 在维护命令中选择 `NMT Start`；
3. 记录 HTTP 返回和 `command_id`；
4. 等待命令 ACK；
5. 在 MQTT 消息流或 CAN 分析仪检查状态。

**预期结果：**

- 请求成功且返回可追踪的命令标识；
- 命令最终状态为成功；
- 节点进入 `OPERATIONAL`；
- 后续状态/PDO 正常上报；
- 目标以外的节点不改变状态。

### TC-CAN-005 NMT Stop 与恢复

**页面：** `/debug/device-control`、`/debug/mqtt-stream`。

**步骤：**

1. 对测试节点发送 `NMT Stop`；
2. 确认节点进入 `STOPPED`；
3. 检查心跳是否仍按协议约定存在；
4. 尝试观察业务 PDO 是否停止；
5. 再发送 `NMT Start` 恢复。

**预期结果：**

- Stop 和 Start 都有明确 ACK；
- 状态顺序正确；
- Stop 后节点不会继续执行不允许的业务通信；
- Start 后恢复正常；
- 其他节点不受影响。

### TC-CAN-006 NMT Reset 与 Boot-up

**页面：** `/debug/device-control`、`/debug/mqtt-stream`。

**步骤：**

1. 记录节点当前状态和安全属性值；
2. 发送 `NMT Reset` 并确认二次提示；
3. 观察节点短暂离线、Boot-up、Pre-operational/Operational 和心跳恢复过程；
4. 检查设备状态重新加载；
5. 核对持久化配置是否符合固件设计。

**预期结果：**

- Reset 有明确 ACK 或可解释的重启中状态；
- CAN 总线出现 Boot-up 帧；
- 节点在规定超时时间内恢复心跳；
- 前端不会永久停留在旧状态；
- 不发生重复执行旧命令。

### TC-CAN-007 SDO 读取与 OD Dump

**页面：** `/debug/od`。

**步骤：**

1. 选择主机、节点、目标和正确 OD 规范版本；
2. 记录当前快照的 `dump_id` 或开始时间；
3. 点击开始 Dump；
4. 等待本次任务完成；
5. 检查新快照和规范对比结果；
6. 保存异常项列表。

**预期结果：**

- Dump 命令下发成功；
- 前端最终读取到本次操作产生的新快照，而不是旧快照；
- 快照 `exists=true` 且 `completed=true`；
- 快照内容非空；
- 可读 OD 条目能够完成 SDO Upload；
- “实机未上报”“规范未定义”“值不一致”均有可解释原因；
- 默认 Dump 应在 60 秒页面超时前完成，具体性能门槛见项目协议。

### TC-CAN-008 安全属性写入与回读

**页面：** `/debug/device-control`、`/debug/mqtt-stream`，必要时使用 `/debug/od`。

**步骤：**

1. 选择固件人员确认的安全 `rw` 属性；
2. 刷新状态并记录原值；
3. 输入一个合法的新值并下发；
4. 记录 `command_id` 和 ACK；
5. 检查设备实际动作或状态上报；
6. 刷新状态或重新 OD Dump；
7. 确认回读值等于新值；
8. 写回原值并再次回读。

**预期结果：**

- 写入请求、CAN SDO Download 和最终 ACK 可关联；
- 设备只执行一次；
- 实际动作、MQTT 状态、页面显示和 SDO 回读一致；
- 原值能够恢复；
- 目标以外节点和属性不改变。

### TC-CAN-009 非法写入与 SDO Abort

**页面：** `/debug/device-control`，辅助使用 `/history/serial`。

**步骤：**

1. 尝试写入页面标记为只读的属性；
2. 对有范围限制的属性输入越界值；
3. 在高级模式使用一个测试用的无效属性编码；
4. 记录前端、后端、主机和 CANopen Abort 结果。

**预期结果：**

- 只读属性在页面被禁止，后端也应独立校验；
- 越界值和无效对象被拒绝；
- 返回结果包含可定位的错误，不得显示为成功；
- 节点原值不变；
- 不影响后续正常命令。

### TC-CAN-010 PDO/实时状态上报

**页面：** `/debug/mqtt-stream`、`/history/sensors`。

**步骤：**

1. 确认节点处于 `OPERATIONAL`；
2. 安全地改变一个会触发 TPDO 或实时状态上报的输入；
3. 记录设备变化时间、CAN 帧时间、MQTT 时间和页面时间；
4. 连续改变多组值；
5. 检查历史数据是否持续入库。

**预期结果：**

- TPDO 或等效状态上报及时产生；
- 数值、单位、符号和缩放正确；
- Node ID、主机 UUID 和属性不会串线；
- 重复值处理符合协议设计；
- 历史记录时间连续且没有明显重复或缺口。

如果当前固件不使用 PDO，应在报告中标记“不适用”，并说明替代的状态上报机制。

### TC-CAN-011 EMCY 产生、记录与恢复

**页面：** `/history/emcy`、`/debug/mqtt-stream`、`/history/serial`。

**步骤：**

1. 清楚记录测试前已有 EMCY，不要直接删除现场证据；
2. 使用固件故障注入、仿真器或安全条件触发一个已知故障；
3. 刷新 EMCY 日志；
4. 核对 Node ID、`error_code`、`register` 和 5 字节厂商数据；
5. 清除故障；
6. 检查设备恢复和错误复位报文。

**预期结果：**

- EMCY 来自正确节点；
- 页面、MQTT 和 CAN 报文内容一致；
- 时间顺序正确；
- 故障清除后节点恢复；
- 同一事件不会被无限重复记录。

### TC-CAN-012 心跳丢失与节点恢复

**页面：** `/debug/mqtt-stream`、`/debug/devices`、`/devices/nodes`。

**步骤：**

1. 在安全条件下停止节点心跳、断开测试节点或关闭节点电源；
2. 记录最后心跳时间；
3. 观察主机和平台的离线判定；
4. 恢复节点连接或电源；
5. 观察 Boot-up、心跳和业务状态恢复。

**预期结果：**

- 节点在协议规定的超时时间内被判定离线；
- 只影响目标节点；
- 恢复后重新出现 Boot-up/心跳；
- 平台状态恢复在线；
- 页面不长期保留离线前的旧业务值；
- 不自动重放可能产生危险动作的旧命令。

### TC-CAN-013 MQTT/WebSocket 中断与恢复

**页面：** `/debug/mqtt-stream`、`/debug/device-control`。

**步骤：**

1. 建立 MQTT 消息流连接；
2. 在测试环境临时中断浏览器到后端的 WebSocket，或重启测试 MQTT/后端服务；
3. 观察页面连接状态和重连行为；
4. 服务恢复后等待自动重连；
5. 刷新设备状态并发送一个安全命令。

**预期结果：**

- 页面明确显示连接异常，不能伪装成实时在线；
- WebSocket 按退避策略自动重连；
- 恢复后能继续接收新消息；
- 中断期间未确认的命令不会错误显示为成功；
- 不重复执行恢复前的旧命令。

### TC-CAN-014 多节点隔离

**页面：** `/debug/device-control`、`/debug/mqtt-stream`、`/debug/od`。

**前置条件：** 同一主机连接至少两个不同 Node ID 的节点。

**步骤：**

1. 同时观察两个节点的心跳；
2. 只对节点 A 执行 NMT Stop；
3. 确认节点 B 保持原状态；
4. 只修改节点 B 的安全属性；
5. 分别执行节点 A、B 的 OD Dump；
6. 核对快照、ACK 和状态归属。

**预期结果：**

- 所有命令只作用于目标 Node ID；
- 状态、快照、ACK 和 EMCY 均归属正确；
- 不出现属性值、设备型号或 OD 快照串节点；
- 两节点同时通信时没有明显丢帧或异常超时。

### TC-CAN-015 主机重启恢复

**页面：** `/debug/device-control`、`/debug/mqtt-stream`、`/debug/devices`。

**步骤：**

1. 确认所有测试节点在线；
2. 在测试环境执行主机软重启；
3. 记录主机离线和重新上线时间；
4. 检查 CAN 初始化、节点发现和心跳恢复；
5. 刷新状态并执行一次安全读写闭环。

**预期结果：**

- 主机能够自动重新连接 MQTT；
- CAN 接口重新初始化；
- 节点重新发现且状态正确；
- 不产生重复 Node ID 或幽灵在线节点；
- 重启前未完成命令有明确的失败或超时结果。

### TC-CAN-016 权限、审计和错误提示

**页面：** 所有核心测试页面，辅助使用 `/history/audit`。

**步骤：**

1. 分别使用允许角色和无权限角色访问核心页面；
2. 使用允许角色执行一个安全写入和 NMT 操作；
3. 检查审计记录；
4. 模拟设备离线后下发命令；
5. 检查页面错误提示。

**预期结果：**

- 无权限角色看不到入口且直接访问被拦截；
- 写操作记录操作者、目标、动作、时间和结果；
- 离线、超时、SDO Abort、权限不足等错误不会统一显示成“发送成功”；
- 页面错误信息足以支持定位且不泄露敏感信息。

## 9. 稳定性与性能测试

### 9.1 建议场景

- 最低冒烟：连续运行 30 分钟；
- 版本验收：连续运行 8 小时；
- 现场稳定性：按项目要求运行 24～72 小时；
- 多节点同时心跳和 PDO 上报；
- 定期执行安全属性读写；
- 间隔执行 OD Dump；
- 测试期间插入一次节点断线恢复和一次主机/MQTT 重连。

### 9.2 记录指标

| 指标 | 记录方法 |
|---|---|
| 心跳应收数、实收数、丢失数 | 按配置周期和运行时长计算 |
| 命令发送数、成功数、失败数、超时数 | 按 `command_id` 去重统计 |
| 命令端到端延迟 | 前端发送时间到成功 ACK 或状态生效时间 |
| OD Dump 成功率和耗时 | 每轮记录开始、完成和快照时间 |
| MQTT/WebSocket 重连次数 | 浏览器、后端和 MQTT 日志联合统计 |
| CAN 错误 | error passive、bus off、重发和错误计数 |
| 状态错乱 | 串节点、旧值覆盖新值、重复执行 |

具体延迟、丢包和成功率门槛应由产品或通信协议要求确定。没有正式指标时，至少要求测试期间无未解释的命令失败、节点串线、重复动作、持续离线或 bus off。

## 10. 整体验收标准

全部满足以下条件才可判定“CANopen 整体通信通过”：

- [×] 前端 CANopen 工具测试通过；
- [ ] 主机与节点绑定、Node ID、型号和 OD 版本正确；
- [ ] 心跳稳定，在线/离线判断正确；
- [ ] NMT Start、Stop、Reset 状态转换正确；
- [ ] SDO 读取成功，OD Dump 生成本次新快照；
- [ ] 安全属性 SDO 写入成功，并完成实际状态和回读双重验证；
- [ ] 非法写入被拒绝且原值不变；
- [ ] PDO 或替代实时状态上报正确；
- [ ] EMCY 内容、节点归属和恢复过程正确；
- [ ] 节点、主机、MQTT/WebSocket 中断后能够正确恢复；
- [ ] 多节点之间没有命令、状态、ACK 或快照串线；
- [ ] 每条写命令都有唯一可追踪的 `command_id` 和最终状态；
- [ ] HTTP、MQTT、CAN、设备实际行为和前端展示一致；
- [ ] 权限和审计符合要求；
- [ ] 所有安全属性均已恢复到测试前状态；
- [ ] 阻断级和严重级缺陷为 0。

以下情况必须判定不通过：

- 页面提示成功但设备未执行；
- 设备已执行但平台没有 ACK 或最终状态；
- 命令执行到错误节点；
- 写入后无法回读或无法恢复原值；
- 使用了上一次 OD Dump 的旧快照；
- 节点掉线后仍长期显示在线；
- 恢复连接后自动重复执行旧命令；
- EMCY 节点、错误码或数据记录错误；
- 出现未解释的 bus off、持续丢帧或状态串线。

## 11. 故障定位方法

### 11.1 按链路定位

| 现象 | 优先检查 |
|---|---|
| 页面没有发出 HTTP 请求 | 页面校验、按钮状态、权限、前端异常 |
| HTTP 4xx | 请求参数、权限、型号绑定、值域、只读限制 |
| HTTP 5xx | 后端日志、数据库、MQTT 客户端状态 |
| HTTP 成功但没有 MQTT 下行 | 后端命令路由、topic、MQTT 连接和发布结果 |
| 有 MQTT 下行但没有 CAN 帧 | 主机命令解析、Node ID 映射、CAN 接口状态 |
| 有 CAN 请求但节点无响应 | 接线、终端电阻、波特率、Node ID、NMT 状态、节点固件 |
| 节点返回 SDO Abort | index/sub-index、访问权限、长度、类型、范围 |
| CAN 已响应但没有 MQTT 上行 | 主机 CAN 解析、命令关联、上行 topic |
| MQTT 已上行但前端不更新 | 后端消费、WebSocket、消息类型、前端过滤和状态映射 |
| ACK 成功但设备行为不符 | ACK 语义、主机提前确认、节点执行逻辑、状态回读 |
| OD Dump 完成但快照为空 | 节点 Dump/SDO 实现、上报 target、后端快照入库 |
| 多节点数据串线 | device_id/Node ID 映射、topic、缓存键、快照查询参数 |

### 11.2 COB-ID 快速核对

以下为 CANopen 常用默认 COB-ID，仅用于辅助核对；项目自定义映射以设备规范为准：

| 类型 | 默认 COB-ID |
|---|---|
| NMT | `0x000` |
| EMCY | `0x080 + Node ID` |
| TPDO1 | `0x180 + Node ID` |
| RPDO1 | `0x200 + Node ID` |
| SDO 响应 | `0x580 + Node ID` |
| SDO 请求 | `0x600 + Node ID` |
| Heartbeat/Boot-up | `0x700 + Node ID` |

## 13. 安全与恢复要求

- 所有写入测试必须先记录原值，并在用例结束后恢复；
- NMT Reset、主机重启、断线和故障注入必须在测试环境或维护窗口执行；
- 禁止通过短路、电源过压、过热或机械堵转等危险方式制造 EMCY；
- 设备连接真实负载时，必须有现场监护人和紧急停止手段；
- 未确认 ACK 含义前，不能把“MQTT 已发布”视为“节点已执行”；
- 测试失败后先停止继续写入，保存 HTTP、MQTT、CAN 和主机日志证据；
- 测试结束后确认所有节点回到预期 NMT 状态、所有属性恢复原值、临时故障注入关闭；
- 不应为了测试而清除无法恢复的生产 EMCY、审计或设备日志。
