# 型号属性查看与 Configs 发布契约

> 本文档取代旧的“上传 JSON / 全量覆盖型号索引”流程。`iot_server_frontend` 不再创建、编辑、导入或发布型号属性。

## 职责边界

- Configs：属性编辑、版本管理、导出和发布。
- IoT 后端：发布包校验、存储、激活，并提供当前生效属性、控制 Schema 和命令下发接口。
- `iot_server_frontend`：只读查看当前生效属性，按后端 Schema 通用渲染控件并发送命令。

## 当前生效属性

```http
GET /api/v1/hn-models/{model_id}/indexes
```

建议后端响应：

```json
{
  "items": [
    {
      "attr_code": "light_brightness",
      "attr_name": "Light brightness",
      "co_index": null,
      "co_sub_index": null,
      "data_type": "UNSIGNED8",
      "access_type": "RW",
      "min_val": 0,
      "max_val": 100,
      "unit": "%",
      "category": "light"
    }
  ],
  "publication": {
    "source_name": "Configs product release package",
    "product_model": "P-0050",
    "config_version": "2026.09.1",
    "profile_id": "profile-uuid",
    "published_at": "2026-09-10T10:00:00Z",
    "is_active": true
  }
}
```

为兼容过渡期，前端仍接受直接返回属性数组的旧响应，但发布来源字段将无法完整展示。后端应补齐 `publication` 字段。

`co_index` 和 `co_sub_index` 允许为空。MQTT 业务属性必须提供唯一的 `attr_code`。

## 已废弃的写入路径

```http
PUT /api/v1/hn-models/{model_id}/indexes
```

前端不再调用该接口，也不再提供上传 JSON、合并导入、覆盖导入或保存导入操作。属性变更必须在 Configs 中完成并通过 IoT 后端发布、激活。

## 控制接口选择

- 有 `idx` 的正式 OD Widget：`POST /api/v1/pods/{pod_id}/widgets/operate`
- 无 `idx` 但有 `attr_code` 的 MQTT 属性：`POST /api/v1/pods/{pod_id}/control`

MQTT 属性命令示例：

```json
{
  "attr_code": "wifi_provisioning",
  "value": true,
  "target_uuid": "device-instance-uuid"
}
```

控件类型、值域、单位、可见性、读写权限和设备实例均以后端控制 Schema 为准，不在前端写死具体产品型号或属性。
