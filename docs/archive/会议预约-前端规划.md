## 1. 目标与边界

### 1.1 产品目标

前端提供静音仓预约和设备自动化状态入口，使用户可以：

- 查询已开通预约能力的静音仓在指定时间段内是否可用；
- 创建、修改和取消自己有权限操作的预约；
- 通过日历和列表查看预约；
- 查看预约是否已经生成设备任务，以及任务是否收到真实 ACK；
- 由管理员显式开通或停用某个静音仓的本地预约能力；
- 由管理员维护第三方会议室到静音仓房间配置的映射；
- 由平台管理员用统一入口配置钉钉、企业微信、飞书等第三方平台连接。

### 1.2 本模块不做什么

- 不实现音视频会议、屏幕共享、录制、转写或会议链接生成；
- 不在前端直接连接 MQTT；
- 不在浏览器中保存或解密第三方应用凭证；
- 不绕过后端 scope 判断来展示其他公司的预约；
- 不把设备命令 `sent` 展示为执行成功；
- 不在第一期实现拖拽改期、循环会议和多平台双向同步；统一框架不等于首版同时交付所有 Provider。

## 2. 当前前端事实

- 技术栈是 Vue 2.6、BootstrapVue 2.23、Vue Router 3 和自定义 Webpack 5。
- 项目没有 Vuex/Pinia；页面数据使用组件本地状态，跨页面筛选条件优先放在 URL query。
- 所有请求必须复用 `src/api/http.js`，业务组件禁止直接使用 axios。
- 路由在 `src/router/index.js` 中显式注册，并使用懒加载。
- 侧栏在 `src/components/Sidebar.vue` 中显式维护。
- 数据主表必须使用全局 `base-table`，不能直接使用 `b-table`。
- 所有文案、路由标题、提示和确认框必须使用 i18n key，并同步八种语言。
- 页面必须兼容深色主题和全局三档字号。
- 当前依赖中没有日历组件或专用时区库；开始实现前要先决定日历渲染和时区转换方案。

## 3. 信息架构与路由

### 3.1 侧栏位置

会议预约不新增顶级分组，复用现有“静音仓管理”分组。现有“型号”和“列表”保留，预约页面作为同级子项；分组默认业务入口调整为静音仓列表，点击分组也可以只展开而不强制跳转。

```text
静音仓管理
├── 型号
├── 列表             含现有设备状态、设备控制和命令历史
├── 预约日历
├── 预约列表
└── 预约配置         按标签页和角色显示
```

新建、编辑和详情属于业务流程页面，不单独占用侧栏菜单。

菜单归组不改变代码边界：预约页面、API 模块和 `/meetings/...` 路由仍独立维护，不能把会议逻辑写进 `Pods.vue`。预约子项按会议模块角色权限显示，不复用 `MENU_KEY.UNITS` 直接放行；某个公司或当前查询结果暂时没有可预约 Unit 时，页面展示稳定空态，不通过扫描当前列表动态增删菜单，避免侧栏闪烁和入口不稳定。

并非所有静音仓都支持预约。Unit 在线、已激活、绑定了 Fan/Light/综合控制节点或能够执行设备命令，均不能作为可预约判断。前端只消费后端返回的预约能力，不从设备节点和控制状态自行推断。

### 3.2 计划路由

| 路由 | 页面 | 菜单展示 |
|---|---|---:|
| `/meetings/calendar` | 预约日历 | 是 |
| `/meetings/bookings` | 预约列表 | 是 |
| `/meetings/bookings/new` | 新建预约 | 否 |
| `/meetings/bookings/:bookingUuid` | 预约详情 | 否 |
| `/meetings/bookings/:bookingUuid/edit` | 编辑预约 | 否 |
| `/meetings/settings` | 预约配置（本地预约/第三方平台/会议室绑定） | 按角色 |

所有路由使用 `meta.title` i18n key。路由和侧栏只负责入口防呆，最终权限以后端响应为准。

注册路由时必须把 `/meetings/bookings/new` 放在 `:bookingUuid` 动态路由之前，避免 `new` 被识别为预约 UUID。

## 4. 页面规格

### 4.1 预约日历

默认入口，第一期支持日视图和周视图。

页面区域：

1. 顶部工具栏：今天、上一周期、下一周期、日/周切换、新建预约；
2. 筛选区：公司、Unit、时区；
3. 时间网格：按 Unit 或日期展示预约块；
4. 图例：即将开始、进行中、已结束、已取消、设备控制异常；
5. 移动端降级为按日期分组的卡片列表。

交互规则：

- 点击空白时间段打开新建页面，并预填 Unit、开始和结束时间；
- 点击预约块打开详情；
- Unit 维度和筛选项只使用后端返回的 `booking_capability=enabled` 静音仓；
- 第一版不支持拖拽和拉伸改期，避免误操作及并发冲突；
- 请求必须携带明确的 `from/to`，默认当前周，禁止一次拉取超过 90 天；
- 无主题查看权限时，预约块只显示“已占用”、Unit 和时间。

当前项目没有日历依赖。第一期优先实现可测试的日/周网格；如果评估后需要引入第三方日历库，必须单独确认 Vue 2 兼容性、包体积、许可和深色主题适配。

### 4.2 静音仓列表衔接

现有静音仓列表展开区已经承载设备控制、公共操作和命令历史。D1 不在该展开区为所有 Unit 增加固定预约面板，也不把完整预约日历或预约列表嵌入行详情。

只有后端明确返回 `booking_capability=enabled` 时，才允许在对应 Unit 行或详情页显示“预约”和“查看预约”快捷操作：

- “预约”跳转 `/meetings/bookings/new?unit_uuid=...`；
- “查看预约”跳转 `/meetings/calendar?unit_uuid=...`；
- `disabled/unconfigured` 对普通用户不显示预约操作；管理员可以看到“预约配置”入口及不可预约原因；
- 快捷入口只是导航，目标页面仍必须重新拉取配置并由后端校验；
- 如果静音仓列表 API 尚未提供权威预约能力摘要，D1 宁可不显示行内快捷入口，也不能为每行发送请求或根据设备节点猜测。

预约能力状态只用于 UI 引导，建议文案为“可预约”“预约已停用”“未开通预约”。状态不能与 Unit 的“已激活”和在线状态合并。

### 4.3 预约列表

使用 `base-table` 展示：

- 会议主题；
- 开始和结束时间；
- Unit；
- 业务生命周期；
- 来源：本系统、第三方平台；第三方来源同时显示 Provider 名称；
- 自动化状态；
- 调度摘要；
- 操作列。

支持时间窗口、公司、Unit、生命周期、来源和自动化状态筛选。筛选条件写入 URL query，刷新或分享链接后可恢复。

操作列根据权限显示查看、编辑、取消和重试。操作列遵循项目的 `actions-cell` 约定，不写固定宽度。

### 4.4 新建/编辑预约

建议使用独立页面，避免在日历弹窗中堆叠公司、Unit、时区和冲突处理。

表单字段：

- 归属公司：只有拥有多个可写公司或平台管理员时显示；
- Unit：只显示后端可预约 Unit 接口返回的 `booking_capability=enabled` 静音仓；
- 会议主题；
- 日期、开始时间、结束时间；
- 时区；
- 参会人数，可选；
- 自动控制摘要，只读。

保存规则：

- 前端做必填、时间先后和合理时长校验；
- 后端冲突结果是权威，前端不能仅凭日历缓存判断可用；
- 创建时生成一次性 `Idempotency-Key`，请求失败重试时复用，用户修改表单后重新生成；
- 编辑提交当前 `revision`，收到版本冲突后提示重新载入，不能覆盖他人的修改；
- MQTT 关闭、设备离线或自动化未配置时仍允许保存预约。
- 提交前即使 Unit 曾在可预约列表中，仍要处理后端最新返回的 `UNIT_NOT_BOOKABLE`，不能用旧缓存继续提交。

### 4.5 预约详情

详情页分为四个区域：

1. 基本信息：主题、时间、Unit、公司、来源和生命周期；
2. 自动化摘要：已配置、未配置、待连接、部分失败等；
3. 调度时间线：计划动作、计划时间、当前状态和最近错误摘要；
4. 变更历史：创建、修改、取消和外部同步记录。

页面操作：

- 有写权限时显示编辑和取消；
- 管理员或维护人员按后端权限显示失败任务重试；
- 取消必须二次确认；
- 设备命令明细和 ACK 只向后端允许的角色展示；
- 维护人员看到的主题必须隐藏或模糊。

### 4.6 预约配置

预约配置使用一个页面、三个标签页，统一路由为 `/meetings/settings`。页面入口只在用户至少能访问一个标签页时显示；切换标签使用 `?tab=local|providers|rooms`，刷新和分享链接后保持当前标签。无权标签不渲染、不允许通过手工修改 query 进入，最终仍以后端权限为准。

```text
预约配置
├── 本地预约       platform_admin/admin/maintainer
├── 第三方平台     仅 platform_admin
└── 会议室绑定     platform_admin/admin/maintainer
```

三个标签页共享公司筛选和当前 scope，但数据、loading、错误和保存状态分别维护，不能因为放在同一页面就混用权限或请求模型。

#### 4.6.1 本地预约

用于维护静音仓房间配置，并显式开通或停用 Unit 的平台内预约能力。没有房间配置的 Unit 视为 `unconfigured`，不能在本系统创建预约；外部预约是否可同步由连接和外部映射另行判断。

使用 `base-table` 展示公司、Unit、时区、预约启用状态和自动化配置状态。新增/编辑规则：

- 先选择公司，再选择同一公司 scope 内的 Unit；
- 同一 Unit 最多一条房间配置；Unit 归属变化时由后端重新校验配置公司；
- 自动化动作通过后端 control-schema 选择节点、属性和值，禁止自由填写固件命令；
- 对门锁等安全动作显示明显风险提示；
- 自动化未配置不等于预约未开通，两种状态必须分开显示；
- 启用“本系统预约”前必须确认该房间没有启用中的第三方映射；若有则引导用户先到“会议室绑定”停用并处理未来预约，不能由前端静默切换；
- 停用前显示未来有效预约数量，明确提示不会自动删除或取消已有预约；用户确认保留后提交 `existing_booking_policy=keep`，需要停止的预约必须逐条取消。

#### 4.6.2 第三方平台

第一版仅 `platform_admin` 可见。该标签解决“本系统能否连接这家公司的某个第三方会议平台”，不负责绑定具体静音仓，也不为每个平台新增菜单或独立设置页。

页面先从 `/meeting-providers` 获取后端已安装的 Provider 元数据，再展示连接名称、公司、Provider、同步方向、启用状态、实际能力、连接测试、最近同步时间和脱敏错误码。支持创建、停用、轮换凭证、连接测试和手工同步。

创建连接时先选 Provider，再按后端返回的字段描述渲染配置表单；字段描述只允许白名单控件（文本、密码、选择、布尔等），不得执行服务端下发的脚本或 HTML。凭证输入只在创建或轮换时出现；保存成功后只显示“已配置”，永不回显 Secret、完整 Key 或 Token。连接测试后，用能力标签明确显示“可列出会议室”“可验证 ID”“支持回调”“支持拉取”等实际能力。

通用页面不得出现 `provider === 'dingtalk'` 之类决定核心流程的判断。平台差异通过显示名称、字段描述、能力和帮助链接表达；如果 Provider 暂未安装，页面显示“不支持”，不能让用户提交一个任意 Provider 字符串。

#### 4.6.3 会议室绑定

用于把某个第三方平台中的会议室 A 显式绑定到当前公司 scope 内的静音仓房间配置 B。该标签不在第三方平台创建会议室，也不能按名称自动绑定。

映射采用向导式流程：

```text
选择公司
  → 选择已配置且连接可用的第三方平台连接
  → 查看连接测试状态
  → 按连接能力列出候选，或输入并验证外部会议室 A
  → 选择当前 scope 内的静音仓房间配置 B
  → 后端验证 external_room_id、公司归属、重复映射和房间配置状态
  → 保存为未启用映射
  → 管理员确认后启用
```

会议室 A 的候选来源由后端统一返回并如实展示，例如 `official_list`、`calendar_event` 或 `manual`。页面动作由连接实际能力决定：有 `room_list` 才显示“加载会议室”，有 `room_verify` 才允许“手工输入并验证”，有 `poll_changes` 才显示“同步测试日程”。某个平台没有企业会议室列表能力时，不得承诺自动加载全部会议室。

没有候选项时显示“尚未发现会议室”，并只提供当前连接实际支持的恢复动作。会议室名称只用于辅助确认；候选项未验证、未选择房间配置或映射未启用时，均不得显示为“已接入”。停用映射前提示其对该连接后续事件的影响。浏览器不得直接调用任何第三方平台接口，候选加载和验证全部经过本系统后端。

MVP 必须把“已配置”和“当前预约主来源”分开显示：同一静音仓可以保存多个 Provider 的候选映射，但只允许启用本系统预约或其中一条外部映射。切换时调用后端单一 `switch-source` 原子接口，不得由前端连续发送“停用旧来源、启用新来源”两个请求。若存在未来预约，页面按后端稳定错误码阻止操作并引导处理。多来源同时可写要等后续双向忙闲同步能力完成后再开放。

## 5. 核心用户流程

### 5.1 创建预约

```text
日历/列表
  → 新建预约
  → 选择公司与 Unit
  → 填写时间和主题
  → 前端基础校验
  → 后端 scope 与冲突校验
  → 保存成功
  → 进入详情并展示自动化状态
```

### 5.2 修改预约

```text
详情
  → 编辑
  → 携带 revision 提交
  ├── 成功：显示新 revision 和新调度摘要
  └── 409 版本冲突：重新加载后由用户确认再次修改
```

### 5.3 取消预约

```text
详情/列表
  → 二次确认
  → 幂等取消
  → 生命周期显示“已取消”
  → 未执行调度任务显示“已取消”
```

取消预约不等于浏览器直接控制门锁；任何补偿动作都由后端安全策略决定。

### 5.4 第三方会议室绑定与预约同步

```text
第三方平台管理员先创建或确认会议室 A
  → 平台管理员在本系统选择 Provider、配置公司连接并通过连接测试
  → 本后台按实际能力加载候选，或手工验证 A.external_room_id
  → 管理员选择公司自己的静音仓 B
  → 保存并启用 A → B 映射
  → 员工在该第三方平台预约、修改或取消 A
  → 后端对应适配器同步并标准化事件，按映射找到 B
  → 本系统创建、更新或取消 B 的预约
```

连接成功、实际能力可用、会议室候选已发现、外部 ID 已验证、映射已启用和日程同步正常是不同状态，页面不得合并成一个“已接入”布尔值。系统可接多个 Provider，同一静音仓也可预配置多个映射，但 MVP 只允许一个预约主来源启用；所有历史和当前预约仍共享同一日历与冲突规则。

## 6. 状态与异常展示

### 6.1 两套状态分开展示

预约生命周期与设备调度状态不能合并成一个状态字段：

| 类型 | 前端文案示例 |
|---|---|
| `upcoming/active/completed/cancelled` | 即将开始/进行中/已结束/已取消 |
| `pending/claimed` | 等待自动控制 |
| `sent` | 指令已发送，等待设备确认 |
| `acknowledged` | 设备已确认 |
| `blocked` | 自动控制待连接 |
| `retry_wait` | 等待重试 |
| `failed` | 自动控制失败 |
| `missed` | 已错过执行窗口 |

不得把 `sent` 翻译为“执行成功”。

### 6.2 页面通用状态

每个页面都要有：

- 首次加载骨架或 loading；
- 空数据说明和可执行下一步；
- API 失败提示及重试按钮；
- 无 scope 的明确空态；
- 提交中的按钮禁用，防止重复操作；
- 离开未保存表单前的确认。

### 6.3 稳定错误码映射

前端按后端 `code` 映射 i18n 文案：

| code | 前端处理 |
|---|---|
| `INVALID_TIME_RANGE` | 聚焦时间字段 |
| `BOOKING_TIME_CONFLICT` | 显示冲突时间段，不泄露无权主题 |
| `BOOKING_REVISION_CONFLICT` | 提示数据已变化并提供重新载入 |
| `BOOKING_CONFIG_IN_USE` | 显示未来预约数量，要求确认保留策略后再停用配置 |
| `BOOKING_SOURCE_IN_USE` | 显示未来预约数量，要求先处理预约再切换主来源 |
| `BOOKING_SOURCE_CONFLICT` | 展示当前启用的本系统或第三方主来源，并提供前往对应配置的入口 |
| `MEETING_BOOKING_NOT_FOUND` | 显示不存在或无权访问 |
| `UNIT_NOT_BOOKABLE` | 从可选项移除该 Unit，并按 `details.reason` 提示“未开通预约”“预约已停用”或“静音仓已停用” |
| `MEETING_PROVIDER_UNSUPPORTED` | 显示该平台尚未由后端安装或已停用，不允许继续创建连接 |
| `MEETING_CAPABILITY_UNAVAILABLE` | 隐藏或禁用当前连接不支持的操作，并提示重新测试权限或改用受支持方式 |
| `EXTERNAL_ROOM_UNVERIFIED` | 保留管理员输入，提示外部会议室 ID 或权限验证失败，禁止启用映射 |
| `EXTERNAL_ROOM_MAPPING_CONFLICT` | 提示该连接中的会议室或目标房间已存在冲突映射，跳转查看现有映射 |
| `INTEGRATION_CONNECTION_UNAVAILABLE` | 显示该连接不可用和重试入口；不阻断本地预约与设备控制 |
| `DEVICE_DISPATCH_UNAVAILABLE` | 仅重试动作报错，预约本身仍有效 |

未知错误使用统一兜底文案，并保留后端 trace/request ID 供排障；不直接展示原始响应正文。

## 7. 权限与隐私

| 能力 | platform_admin | admin | data_entry | maintainer | viewer |
|---|---:|---:|---:|---:|---:|
| 查看预约 | 全部 | scope 内 | scope 内 | scope 内摘要 | scope 内 |
| 创建/编辑/取消 | 是 | scope 内 | scope 内 | 否 | 否 |
| 重试调度 | 是 | scope 内 | 否 | scope 内 | 否 |
| 本地预约配置 | 是 | scope 内 | 否 | scope 内 | 否 |
| 第三方平台/凭证 | 是 | 否 | 否 | 否 | 否 |
| 会议室绑定 | 是 | scope 内 | 否 | scope 内 | 否 |

前端实施要求：

- 在 `src/utils/permission.js` 增加会议模块菜单键和操作判断；
- 静音仓分组按“任一可见子项”决定是否展示，预约子项不能因用户拥有 `UNITS` 菜单权限而自动显示；
- 命名路由能力、侧栏和按钮使用 `src/utils/permission.js` 的同一能力定义；
- 后端 403/404 仍是最终结果，不能依赖隐藏按钮保障安全；
- 维护人员不显示会议主题；
- 日历冲突块对无权用户只显示占用时间；
- 不缓存第三方凭证、完整 Webhook 或完整参会人数据。

## 8. API 对接规划

前端 API 路径不带 `/api/v1`，由 `src/api/http.js` 的 baseURL 统一提供。

第三方平台的 Token、日程、参会人和会议室接口只允许后端适配器调用，前端不得直接请求钉钉、企业微信或其他 Provider。统一业务契约以后端会议预约规格为准；各平台的外部接口和字段映射以对应 Provider 契约为准。

| 前端方法 | 后端资源 |
|---|---|
| `listMeetingBookings(params)` | `GET /meeting-bookings` |
| `getMeetingBooking(uuid)` | `GET /meeting-bookings/{uuid}` |
| `createMeetingBooking(payload, idempotencyKey)` | `POST /meeting-bookings` |
| `updateMeetingBooking(uuid, payload)` | `PATCH /meeting-bookings/{uuid}` |
| `cancelMeetingBooking(uuid)` | `POST /meeting-bookings/{uuid}/cancel` |
| `listMeetingBookingEvents(uuid)` | `GET /meeting-bookings/{uuid}/events` |
| `listMeetingDispatchJobs(uuid)` | `GET /meeting-bookings/{uuid}/dispatch-jobs` |
| `retryMeetingDispatch(uuid)` | `POST /meeting-bookings/{uuid}/retry-dispatch` |
| `listBookableMeetingUnits(params)` | `GET /meeting-room-configs/bookable-units` |
| `listMeetingUnitCapabilities(params)` | `GET /meeting-room-configs/unit-capabilities` |
| `listMeetingRoomConfigs(params)` | `GET /meeting-room-configs` |
| `createMeetingRoomConfig(payload)` | `POST /meeting-room-configs` |
| `updateMeetingRoomConfig(uuid, payload)` | `PATCH /meeting-room-configs/{uuid}` |
| `switchMeetingRoomSource(uuid, payload)` | `POST /meeting-room-configs/{uuid}/switch-source` |
| `listMeetingRoomMappings(params)` | `GET /meeting-room-mappings` |
| `listMeetingProviders()` | `GET /meeting-providers` |
| `listMeetingIntegrations(params)` | `GET /meeting-integrations` |
| `testMeetingIntegration(uuid)` | `POST /meeting-integrations/{uuid}/test` |
| `syncMeetingIntegration(uuid)` | `POST /meeting-integrations/{uuid}/sync` |
| `listExternalRoomCandidates(integrationUuid)` | `GET /meeting-integrations/{uuid}/room-candidates` |
| `verifyExternalRoomCandidate(integrationUuid, payload)` | `POST /meeting-integrations/{uuid}/room-candidates/verify` |

预约配置三个标签页分别调用房间配置、第三方集成和房间映射 API；共用页面不代表共用请求模型。写接口必须等后端 Swagger 契约确定后再落地，前端文档不自行发明字段。`listBookableMeetingUnits` 是日历和新建表单的权威候选源，只返回当前 scope 内已开通本地预约的 Unit；静音仓通用列表不能通过节点绑定、在线状态或自动化配置反推该结果。

列表查询使用 ISO 8601 的 `from/to`。表单提交同时携带带 offset 的 `start_at/end_at` 和 IANA `timezone`。不得用浏览器当前时区静默覆盖用户选择。

任意第三方预约经后端标准化后，前端只消费：

| 后端字段 | 展示含义 |
|---|---|
| `source_type=integration` | 来源类型显示“第三方平台” |
| `source_provider` / `integration_name` | 显示“钉钉”“企业微信”等 Provider 名及连接名称 |
| `subject` | 会议主题，按权限脱敏 |
| `start_at/end_at/timezone` | 会议时间 |
| `participant_count` | 显示“受邀人数”，不能显示为实际到场人数 |
| `room_mapping/unit` | 已映射的静音仓 |
| `external_sync_status` | 同步成功、待处理或失败 |
| `last_error_code` | 映射为 i18n 错误提示，不展示原始响应 |

前端不接收 Secret、Access Token、刷新凭证、完整参会人数组、人员 ID、Webhook 原文或第三方响应正文。

实现约束：

- API 文件只负责请求和最小响应解包，不混入页面状态；
- 日历、列表和详情各自维护 loading/error/data；
- 可分享筛选放 URL query，不引入全局 store；
- 状态文案、颜色和图标集中定义，避免各页面自行判断；
- Provider 配置字段只通过白名单 schema 渲染器生成；Provider 名称不得散落为核心流程条件；
- 日期格式化复用或新增统一工具，不在模板中散落 `new Date()`；
- 不复制后端枚举，未知状态必须有安全兜底显示。

## 10. 视觉、响应式与无障碍

- 使用现有 design tokens 和 CSS 变量，禁止为本模块另建独立暗色主题。
- 字号正常写 px，由现有 PostCSS 转 rem；不注入运行时字号覆盖。
- 桌面端日历最小可用宽度不足时改为横向滚动或列表视图，不能压缩到不可读。
- 移动端默认列表视图，新建表单单列排列。
- 状态不能只用颜色区分，同时提供文字或图标。
- 所有可点击预约块支持键盘聚焦和 Enter/Space 打开。
- 表单 label、错误说明和必填状态必须可被辅助技术识别。
- 所有日期、数字和文案使用当前 locale 格式化。

## 11. 分阶段实施

### 阶段 D1：基础预约

- 新增 API 模块、独立 `/meetings/...` 路由和会议权限键，将预约子项挂入现有“静音仓管理”分组；
- 接入可预约 Unit 查询和 `enabled/disabled/unconfigured` 展示规则；
- 完成本地预约配置的开通、停用和未来预约确认；外部房间映射留到 D3；
- 完成日历、列表、新建/编辑和详情；
- 完成冲突、revision、取消和基础空态；
- 接入八种语言、深色主题和响应式；
- 只依赖后端预约 CRUD，不依赖 MQTT 或真实第三方 Provider。

### 阶段 D2：设备调度可视化

- 增加自动化摘要和调度时间线；
- 增加 blocked、failed、missed 和重试交互；
- 完成维护人员脱敏视图；
- 与一台真实 Unit 完成端到端验证。

### 阶段 D3：统一第三方平台框架与首个 Provider

- 在预约配置页面增加“第三方平台”和“会议室绑定”标签页；
- 按 Provider 元数据渲染连接表单，按实际能力渲染候选、验证和同步动作；
- 先用 fake Provider 完成两套能力组合的前后端合同测试；
- 完成外部会议室 ID 验证和 A → B 启用向导；
- 接入首个真实 Provider（建议钉钉）的凭证、连接测试、轮换、单向同步状态和错误提示。

### 阶段 D4：第二个 Provider 验证抽象

- 接入第二个真实 Provider（建议企业微信），复用同一路由、页面、组件和 API；
- 不新增企业微信专属顶级菜单、业务表或重复页面；
- 若需要专属字段，只扩充后端 Provider 元数据或 Provider 专属帮助内容，不在通用组件硬编码业务分支；
- 用钉钉与企业微信连接并存、不同静音仓分别启用，以及同一静音仓主来源互斥和安全切换的场景完成验收。

### 阶段 D5：更多 Provider 与双向能力

- 每个新 Provider 单独交付契约、帮助内容和验收用例；
- 双向同步只有在后端完成主数据源、冲突与循环更新评审后，才按 `bidirectional` 实际能力开放界面。

## 12. 测试与验收

### 12.1 前端测试

- API 参数、UUID 路径和 Idempotency-Key 正确；
- 日/周时间边界、跨天预约和时区显示正确；
- 409 冲突和 revision 冲突有明确恢复路径；
- 重复点击不会创建两条预约；
- MQTT 关闭时仍能保存预约；
- `sent`、`acknowledged`、`failed` 展示不混淆；
- 五种角色的菜单、路由和按钮符合矩阵；
- 设备可控但未开通预约的 Unit 不出现在日历筛选和新建表单中；
- `enabled/disabled/unconfigured` 三种预约能力不会与 Unit 激活状态或设备在线状态混淆；
- 静音仓列表没有权威预约能力字段时不显示猜测性的行内预约按钮，也不产生逐行 N+1 请求；
- 没有 `room_list` 能力时不显示加载按钮；有 `room_verify` 时可手工验证外部会议室 ID 完成 A → B 映射；名称相同的候选项不会自动绑定；
- 两个 fake Provider 返回不同能力时，页面仅显示各自支持的操作；未知 Provider 不渲染任意配置字段；
- Provider 连接故障只影响该连接页面和同步状态，本地预约、其他连接及静音仓设备控制仍可用；
- 同一静音仓可保存两个 Provider 映射，但只能启用一个；尝试启用第二个或与本地预约并行时显示主来源冲突，完成停用与未来预约处理后可以切换；
- 页面源码、组件状态、浏览器缓存和错误提示中均没有第三方明文凭证；
- 维护人员和无主题权限用户看不到敏感主题；
- 八种语言切换后表格列、按钮和状态立即更新；
- 深色主题、三档字号和移动端布局可用。

### 12.2 联调验收

1. 本地 PostgreSQL 创建预约，日历和列表同时出现；
2. 未开通预约的 Unit 即使在线且设备控制可用，也不能创建预约；
3. 停用预约配置后，该 Unit 从候选项移除，历史预约仍可查看和取消；
4. 制造同 Unit 时间冲突，前端显示时间段但不泄露主题；
5. MQTT 关闭时预约成功，详情显示“自动控制待连接”；
6. MQTT 启用后真实命令从 sent 到 acknowledged；
7. 改期后旧 revision 不再显示为待执行；
8. 取消预约后页面与调度状态一致；
9. fake Provider 完成连接、候选/验证、映射、同步和异常降级全链路；
10. 首个真实 Provider 完成单向同步，第二个 Provider 用相同页面完成接入且未新增核心流程分支；
11. `.38` 演示环境只演示假数据页面，不作为真机 ACK 或真实 Provider 验收结果。
