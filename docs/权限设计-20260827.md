# 权限设计

> 最后更新：2026-09-02
> 适用范围：管理后台菜单、路由、页面操作和后端数据作用域
> 状态：目标权限合同；后端 `maintainer -> operator` 迁移待 `iot_server_backend#21` 实施

## 1. 设计原则

权限由三层共同决定，任何一层都不能替代另外两层：

1. **能力权限**：决定能否进入某个功能，例如平台资产管理、租户用户管理、设备运维。
2. **角色权限**：决定能否执行查看、录入、管理或运维动作。
3. **数据作用域**：决定能读取或修改哪些公司的数据。

`platform_admin` 是当前唯一的平台权限账号。`company_type = PF` 只是公司分类，租户 `admin`、
`operator` 即使属于 PF 公司，也不会自动获得平台级能力。后续增加平台运维角色时，应把角色加入明确的
能力点，不得继续在页面中散落角色或公司类型判断。

前端菜单和路由只负责用户体验；后端必须继续校验角色、资源归属和 scope。

## 2. 角色职责

| 角色 | 定位 | 默认写能力 |
| --- | --- | --- |
| `platform_admin` | 平台超级管理员 | 全局配置、平台资产、平台诊断和租户管理 |
| `admin` | 公司管理员 | 公司所有者/最高权限；管理公司归属、高风险设置及运营授权 |
| `operator` | 运营管理 | scope 内日常业务、设备运维、公司配置及普通用户管理 |
| `data_entry` | 数据录入 | scope 内批量数据、入出库、装配/绑定、文件及必要纠错 |
| `viewer` | 查看员 | 只读业务看板、单元、预约、资料和业务历史 |

## 4. 数据范围

- `platform_admin`：全公司读写。
- 其他角色可读：`allowed_companies`。
- `admin`、`operator`、`data_entry` 可写：必须同时满足动作能力和 `writable_companies`。
- `viewer`：永远没有写作用域。
- 行数据含多个公司归属时（例如单元的厂家、品牌、代理、经销商、最终用户），任一合法归属命中
  `writable_companies` 才能显示相应写操作；后端仍按接口规则作最终判断。
- 未知角色、缺少 `company_type`、缺少 scope 或未登记能力一律 fail-closed。

## 5. 平台资产与租户业务的边界

“型号、主机、节点”页面是平台资产台账，只向 `platform_admin` 提供。租户不直接进入这些平台管理页，
而是在“静音仓/单元”和运维页面中使用已经分配到其 scope 的设备。公司管理员和运营管理可从运维流程
进入 scope 内的单设备详情，但不会获得平台资产全量列表入口。

底层主机、节点查询接口仍可能被文件关联、OTA、设备日志等 scope 化业务使用，因此不能仅凭平台资产菜单
的可见性把所有读取接口粗暴改成平台专属。后端应按调用场景做到：平台管理动作使用平台能力；租户业务
查询只返回 scope 内的最小必要字段；创建、出货、原始诊断和全局枚举继续使用更严格的动作权限。

## 6. 实现约束

- 能力表、菜单映射和命名路由映射统一维护在 `src/utils/permission.js`。
- Sidebar 只消费能力，不再硬编码角色数组。
- Router 对未登记的命名业务路由 fail-closed；直接输入 URL 不能绕过菜单权限。
- 页面按钮使用能力 + 动作角色 + `canWriteCompany`/`canWriteRow`。
- 后端继续使用 `require_roles` 与 scope 校验；任何全局枚举、凭据、原始 MQTT/命令数据均按平台能力处理。
- 新增页面时必须同时补能力映射、路由登记、菜单/业务入口、页面动作判断和权限测试。
- `operator` 必须使用明确能力白名单；用户管理还必须校验目标角色，不得用“管理员减去几项”实现。
- 后端将 `maintainer` 迁移为 `operator` 的合同、数据、令牌和测试要求记录在 `iot_server_backend#21` 的 `users` 表回复中。
